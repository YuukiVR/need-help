# Putting it online — deploying Supabase

Supabase is already a hosted service. You don't upload SQL files or a database
anywhere: you create a project on supabase.com and **push the migrations** to
it over an encrypted connection. The app then talks to
`https://<project-ref>.supabase.co` with the public anon key.

Do the steps in this order. The database first, then users, then the frontend.

---

## 0. Prerequisites

- A GitHub repo with this project (recommended, not required).
- Supabase CLI: `npm install -g supabase`
- Your migrations in `supabase/migrations/` (already done).

---

## 1. Create the hosted project

1. Go to <https://supabase.com/dashboard> → **New project**.
2. Pick the **region closest to your users** — it cannot be changed later
   without recreating the project.
3. Set a strong **database password** and save it in a password manager.
   `supabase link` and `supabase db push` will ask for it.
4. Wait ~2 minutes for provisioning.

Free plan notes: 2 active projects max, ~500 MB database, 1 GB storage,
5 GB egress, and the project **pauses after ~7 days without API traffic**.

---

## 2. Push the schema

```powershell
supabase login                       # opens the browser / asks for an access token
supabase projects list               # find your project ref
supabase link --project-ref <ref>    # asks for the database password
supabase db push --dry-run           # show what will run
supabase db push                     # apply 0001 → 0010
```

> Using CLI v3? It rejects `[inbucket]` in `supabase/config.toml` ("use
> `[local_smtp]` instead"). Either rename that section, or pin the CLI this
> config targets: `npx supabase@2 db push …`. No login is needed when you pass
> a connection string: `npx supabase@2 db push --db-url "<session pooler URL>"`.

`db push` runs the files in filename order and records them in
`supabase_migrations.schema_migrations`, so it is safe to re-run: already
applied migrations are skipped.

**No CLI, or `supabase login` keeps failing?** Open **SQL Editor**, paste the
whole of [`supabase/sql/apply-all.sql`](./supabase/sql/apply-all.sql) (all ten
migrations in order), and run it once. It is generated by
`node scripts/build-sql-bundle.mjs`.

Trade-off: the SQL Editor path does not record migration history, so a later
`supabase db push` will try to re-apply everything. Either keep using the SQL
Editor for schema changes, or run `supabase migration repair` once the CLI
works.

### Verify

In the dashboard → **SQL Editor**:

```sql
-- tables
select tablename from pg_tables where schemaname = 'public' order by 1;

-- RLS must be true on all four
select relname, relrowsecurity
from pg_class
where relnamespace = 'public'::regnamespace
  and relkind = 'r'
order by 1;

-- policies
select tablename, policyname, cmd
from pg_policies
where schemaname = 'public'
order by 1, 2;
```

You should see `profiles`, `reports`, `assignments`, `report_events`,
`relrowsecurity = true` on all four, and the policy list from `0007`.

> If `create trigger on auth.users` fails, run `0002_profiles.sql` manually in
> the SQL Editor. Some older CLI/pooler combinations lack permission there;
> the SQL Editor runs as `postgres` and always works.

## 3. Create the accounts

### The default superadmin (`admin` / `admin`)

Run the provisioning script once against the hosted project:

```powershell
Copy-Item .env.admin.example .env.admin
# edit .env.admin:
#   SUPABASE_URL=https://<ref>.supabase.co
#   SUPABASE_SERVICE_ROLE_KEY=<secret key>   (Project Settings → API → Secret keys)
node --env-file=.env.admin scripts/create-admin.mjs
```

It creates `admin@need-help.local`, confirms the email, sets the password to
`admin`, and makes the profile an active `admin`. Re-running it resets the
password, so it doubles as "I forgot the password".

If Auth refuses the 5-character password, run
[`supabase/sql/force-admin-password.sql`](./supabase/sql/force-admin-password.sql)
in the SQL Editor.

Then check the whole project in one go:

```powershell
node --env-file=.env.admin scripts/verify-deploy.mjs
```

It checks the REST API, all five tables, the `report-photos` bucket, the admin
user, the admin profile, and that anonymous requests get no rows back (RLS).

### Optional demo accounts

Dashboard → **Authentication → Users → Add user**:

| Email | Role (after promotion) |
|---|---|
| `admin@example.com` | admin |
| `responder@example.com` | responder |
| `consumer@example.com` | consumer |

Tick **Auto Confirm User**. The signup trigger creates a `profiles` row as
`consumer`; promote the other two in the SQL Editor:

```sql
update public.profiles p
   set role = 'admin'
  from auth.users u
 where u.id = p.id and u.email = 'admin@example.com';

update public.profiles p
   set role = 'responder'
  from auth.users u
 where u.id = p.id and u.email = 'responder@example.com';
```

Optional demo data: paste `supabase/seed.sql` into the SQL Editor. It only
promotes those three emails and inserts reports if the table is empty.

Do **not** run `supabase db reset --linked` against production. It drops the
schema and all users.

## 4. Configure Auth for a public URL

Dashboard → **Authentication**:

**URL Configuration**
- Site URL: `https://<your-app>.pages.dev` (or your domain)
- Redirect URLs: add both
  - `https://<your-app>.pages.dev/**`
  - `http://localhost:5173/**` (local dev)

**Providers → Email**
- Enable email signups (consumers self-register).
- Enable **Confirm email** once SMTP is configured.

**Emails → SMTP**
- The built-in mailer is rate-limited and meant for testing only.
- Use a free SMTP provider (Resend ~3k/month, Brevo ~300/day) and a verified
  sender domain. Without a verified domain, most providers only deliver to
  your own address.

**Attack Protection**
- Enable CAPTCHA (hCaptcha or Cloudflare Turnstile — both free). Public signup
  without it will attract bots.
- Leave anonymous sign-ins disabled.

## 5. Deploy the frontend

Cloudflare Pages (free, commercial use allowed, unlimited requests):

1. Push this repo to GitHub.
2. Cloudflare Dashboard → **Workers & Pages → Create → Pages → Connect to Git**.
3. Build command `npm run build`, output directory `dist`.
4. Environment variables (Production **and** Preview):
   - `VITE_SUPABASE_URL` = `https://<ref>.supabase.co`
   - `VITE_SUPABASE_ANON_KEY` = the **publishable** key (`sb_publishable_…`) or
     legacy `anon` key (Project Settings → API)
   - `VITE_USERNAME_DOMAIN` = `need-help.local` (same as `USERNAME_DOMAIN`)
   - Do **not** set `VITE_DEMO_MODE`. Demo data is dev-only, but leaving it off
     keeps the deployed console on real data.
5. SPA routing is already handled by [`public/_redirects`](./public/_redirects)
   (`/* /index.html 200`). Without it, a refresh on `/reports` returns 404.
6. Deploy, then add the resulting `*.pages.dev` URL to Supabase **Site URL**
   and **Redirect URLs** (step 4).
7. Custom domain: optional, free to attach if you own the domain.

Check the deploy: open `/login`, sign in as `admin`, and confirm the dashboard
loads real counts. If it says "Cannot reach the server", the Supabase URL or
anon key is wrong.

**Never** put the secret key (`sb_secret_…` / `service_role`) in the frontend or
in a `VITE_` variable. It bypasses RLS. The publishable key is designed to be
public; RLS is what protects your data.

## 6. Go-live checklist

- [ ] RLS enabled on `profiles`, `reports`, `assignments`, `report_events`
- [ ] Default `admin` / `admin` password changed (or the account disabled)
- [ ] `service_role` / secret key exists only on the server / CI, never in the bundle
- [ ] Auth Site URL + redirect URLs point at the real domain
- [ ] CAPTCHA enabled on signup
- [ ] Custom SMTP configured and a test signup email received
- [ ] Keep-alive: cron-job.org (free) hits
      `https://<ref>.supabase.co/rest/v1/health?select=ok` with the header
      `apikey: <anon key>` every 2–3 days, so the free project never pauses
- [ ] Daily backup: `.github/workflows/supabase-backup.yml` + `SUPABASE_DB_URL`
      secret (use the **pooler** connection string, see below)
- [ ] UptimeRobot monitor on the app URL
- [ ] Photos compressed client-side to ~1280 px / quality 0.7 (1 GB fills fast)
- [ ] Three-role smoke test in incognito windows:
      consumer files → admin assigns → responder accepts/completes → consumer
      sees `resolved`
- [ ] Privacy notice, emergency disclaimer, and a phone fallback published

### Backup connection string

GitHub-hosted runners have no IPv6, and Supabase's direct connection is
IPv6-only on the free plan. Use the **Supavisor pooler** string from
Project Settings → Database → Connection string → **Session mode**:

```
postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Store it as the `SUPABASE_DB_URL` GitHub secret.

Storage **files** are not included in `pg_dump` (only metadata). For a pilot,
re-uploading photos is acceptable; for real production, mirror the bucket with
`rclone` or upgrade for backups.

## 7. Day-2: changing the schema

Never edit a migration that has already been applied. Add a new one:

```powershell
supabase migration new add_report_notes
# edit supabase/migrations/<timestamp>_add_report_notes.sql
supabase db reset          # test locally (wipes local data only)
supabase db push           # apply to production
```

Avoid changing the schema in the dashboard. If you must, run
`supabase db pull` immediately so the change is captured as a migration —
otherwise the next `db push` will not match production.

## 8. Optional: deploy migrations from CI

`.github/workflows/supabase-deploy.yml` (manual trigger) needs two secrets:

- `SUPABASE_ACCESS_TOKEN` (Account → Access Tokens)
- `SUPABASE_DB_PASSWORD`

```yaml
name: Deploy database
on:
  workflow_dispatch:
jobs:
  push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
        with:
          version: latest
      - run: supabase link --project-ref ${{ secrets.SUPABASE_PROJECT_REF }}
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
          SUPABASE_DB_PASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}
      - run: supabase db push
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
          SUPABASE_DB_PASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}
```

## 9. Cost and limits (as of writing — verify before launch)

| Item | Free | Breaks at |
|---|---|---|
| Supabase project | 500 MB DB, 1 GB storage, 5 GB egress, 50k MAU | photos + growth; pauses after 7 idle days |
| Cloudflare Pages | unlimited requests, 500 builds/mo | nothing realistic |
| Resend | ~3k emails/mo, 100/day | enough for auth/invites |
| hCaptcha / Turnstile | free | — |
| cron-job.org / UptimeRobot | free | — |
| Domain | `*.pages.dev` free | custom domain ~$10–15/yr |

Total: **$0/month**. The first paid step is Supabase Pro (~$25/mo) for
backups, no pausing, and more storage — worth it once real users depend on
the service during outages.
